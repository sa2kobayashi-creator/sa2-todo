## 販売方針（決定メモ・2026-08-21 改訂）

**販路を2つ持ち、メールボックスを両方共通の有料オプションにする。**

| 販路 | 対象 | 形態 | テナント分離 |
|---|---|---|---|
| **A. 専用インスタンス**（主力） | 事業者・小組織・こだわりの個人 | 顧客ごとに1インスタンス。運営が構築・保守 | インスタンスが分かれるので **不要** |
| **B. 共有インスタンス** | 一般消費者 | 運営が1つ運用し、複数顧客が同居 | 顧客には Standard / Light のみ配る |
| **C. メールボックス**（オプション） | A・B 共通 | `@sa2-plus.com` の実メールボックス | 既存の申請→承認フローを課金ゲートに使う |

### 0. なぜ2本立てにするか

- **A が主力な理由:** 「外部サービスの鍵がアプリ全体で1セット」という現状の設計が、インスタンスを分ければ **そのまま正しい設計になる**。48モデルへの `tenant_id` 追加という大工事が不要。顧客が自分の R2 / DeepL キーを入れる（BYOK）なら API 原価もゼロ。
- **B を併売できる理由:** 消費者は `Standard` / `Light` で、`/settings` にそもそも到達できない（`EnsureFeature:settings` は Admin 以上）。さらに 2026-08-21 に **外部サービスの鍵の書き換えを SuperAdmin 限定に変更**したため、仮に顧客へ Admin を渡してもインフラは触れない。
- **C が効く理由:** 独自ドメインのメールボックスは実コストがあり、Google / iCloud では代替できない。容量課金と違って比較されにくい。

**B の必須運用ルール:** 共有インスタンスの顧客に `admin` を付与しない。付与するのは A（専用インスタンス）の契約代表だけ。

### 0-2. 価格の考え方（重要）

**ストレージ容量を看板にしない。** 比較対象が強すぎる。

| 比較対象 | 月額 | 容量 | 家族共有 |
|---|---|---|---|
| Google One Basic | ¥290 | 100GB | 5人 |
| iCloud+ | ¥540 | 200GB | あり |
| iCloud+ | ¥1,800 | 2TB | あり |
| freee スターター | 実質 ¥980 | — | — |

`¥980/月・20GB・超過 ¥200/10GB` は、容量で見ると Google の 7〜15倍に読める。一方 **¥980 という金額自体は「業務ツール」としては相場どおり**。よって Standard は容量を厚めに込みにして、**容量の話をさせない**のが正解。

### 0-3. 金額案（改訂）

| 商品 | 案 | メモ |
|---|---|---|
| **A. 専用インスタンス 初期** | ¥50,000〜 | 構築・移行・初期設定 |
| **A. 専用インスタンス 保守** | ¥8,000／月〜（5ユーザーまで） | 追加ユーザー ¥1,000／月。ストレージ・API キーは顧客持ち（BYOK） |
| **B. Light** | ¥0 | 20GB。招待制。超過は停止 |
| **B. Standard** | ¥980／月 または ¥9,800／年 | **100GB 込み**（20GB から引き上げ）。周辺メニュー解放 |
| **B. ストレージ超過** | ¥300／100GB／月 | 従来案 ¥200／10GB は割高に見えるため改訂 |

外部 IMAP アカウント（利用者が持つ Gmail 等）の閲覧は **無料のまま**。課金するのは `@sa2-plus.com` の実メールボックスだけ。

### 0-4. メールボックス有料化の実装メモ

課金ゲートは新規に作らなくてよい。既存の申請フロー（`MailDomainRequestController` → 管理者承認 → `Sa2PlusMailboxService` が払い出し）が、そのまま「入金確認後に承認する」ゲートになる。

初版で足すのは次だけ:

1. 申請画面に料金と課金開始タイミングを表示する
2. 解約時にメールボックスを停止する導線（現状は払い出しのみ）
3. Stripe を入れる段階で「サブスク有効 → 自動承認」に差し替える

### 1. 公開しないもの（当面）

| 機能 | 理由 | 実装上の扱い |
|---|---|---|
| **写真鮮明化** | 原価が高く試作段階 | SuperAdmin のみ継続。一般・有料プランにも出さない |
| **Travelpayouts（Travel 運賃目安）** | 契約・UI・汎用化が未成熟 | Travel メニューごと一般公開しない（運営・家族のみ） |

### 2. どこまで公開するか（製品スコープ）

**公開の芯（課金の主戦場）:** Todo / メモ / Photos（鮮明化なし） / メッセージ / メール / マイページ  

**有料 Standard で広げてよい候補:** 入出金 / 路線 / Map / 音楽 / 動画検索 / グループ  

**公開しない・後回し:** 鮮明化、Travel（Travelpayouts）、運営共有キーの DeepL／LLM を「使い放題」で一般開放  

登録は当面 **招待制を維持**（自己登録フルオープンはしない）。公開ベータに進むなら CAPTCHA＋招待 or 承認待ち。

### 3. ロール（Admin / Standard / Light）でよいか

**結論: この3つ＋内部用 SuperAdmin でよい。** 売り物のプラン名と 1:1 対応させる。

| ロール | 製品上の意味 | 販売 |
|---|---|---|
| **Light** | 無料（または低額）の入口。芯機能＋Photos | 自己登録／招待の既定 |
| **Standard** | 通常の有料プラン。仕事・生活の周辺機能 | 月額／年額の本命 |
| **Admin** | 家族・小組織の「設定できる人」。ユーザー管理・祝日・表示メニュー。**外部サービスの鍵は触れない** | 販路 A の契約代表のみ。共有インスタンスの消費者には付与しない |
| **SuperAdmin** | 運営のみ。試作・グローバルキー | 販売しない |

公開時の調整案:

- Standard のデフォルトから **Travel を外す**（Travelpayouts 非公開と一致）
- 翻訳（DeepL）・LLM 音声は **プランに含めず**、当面 SA のみ／将来は有料アドオン or 顧客持ちキー

### 4. 課金・契約（ストレージは成熟、他 API はどうするか）

#### 4A. ストレージ（先行して売る）

既存方針を維持（`commercial-storage.md`）:

- 無料枠 **20GB／ユーザー**
- 超過は停止（3B）→ Stripe で超過解禁（2B）
- 運営共有 R2/B2（モデル A）で開始してよい

**金額は「0-3. 金額案（改訂）」を正とする。** ¥200／10GB／月 の旧案は Google 比で割高に見えるため取り下げ、Standard に 100GB を込み・超過 ¥300／100GB／月 に改めた。

専用インスタンス（販路 A）は顧客がストレージキーを持つため、この超過課金の対象外。

契約形態: **Stripe サブスクリプション**（月／年）。規約・プライバシーは既存。販売前に弁護士レビュー推奨。

#### 4B. DeepL・その他の従量 API

**一般公開の初版では運営キーを開放しない。**

| API | 初版の扱い | 将来 |
|---|---|---|
| DeepL | SA 試作のまま | ①有料アドオン（例: ¥480／月・日次文字上限）②顧客が自分の DeepL キーを登録（BYOK） |
| OpenAI / Gemini（音声） | SA のみ | 同上（アドオン or BYOK） |
| YouTube Data | Standard に残すなら厳しい日次上限 | クォータ枯渇で全体停止しうるので監視必須 |
| Maps | リファラ制限＋予算アラート必須 | Standard に含めてもよいが呼び出し上限を検討 |
| 鮮明化 / Travelpayouts | **非公開** | 製品化するまで触らない |

DeepL を「Standard に込める」のは **原価が見えないうちは非推奨**。ストレージ課金が回ってからアドオン化。

### 5. セキュリティ（公開前に残っている対策）

#### 2026-08-21 に対応済み（全コード監査の結果）

| 重大度 | 項目 | 対応 |
|---|---|---|
| **Critical** | 受信メール本文の保存型 XSS | `MailHtmlSanitizer`（symfony/html-sanitizer）で許可リスト方式に無害化。`script` / `iframe` / `form` / `style` ブロック / `javascript:` / イベントハンドラを除去。表示側は `contain: layout` で重ね物を封じる |

### 6. 進め方（推奨順・改訂）

売上が立つのが早い順に並べる。**専用インスタンス（A）は Stripe を待たずに請求書で売れる。**

1. **A を1社に売る** … 現行コードのまま。BYOK なので API 原価ゼロ。請求書・銀行振込で開始でき、Stripe 実装を待たない
2. **C（メールボックス）を A の顧客と既存ユーザーに出す** … 申請→承認フローが既にあるので、料金表示と解約導線だけ足す
3. **公開スコープをコードに合わせる** … Travel を Standard 既定から外す／鮮明化・Travelpayouts 非表示を再確認
4. **Stripe で B の Standard 月額＋ストレージ超過**（DeepL はまだ売らない）
5. **招待制のまま少人数課金ベータ** → 問題なければ登録開放検討＋ DeepL アドオン or BYOK

## 結論

現状は **運営者（管理者）＋承認した少数ユーザーの生活アプリ** として動く。  
コアデータ（Todo / メモ / 入出金 / Photos の所有者）は `user_id` でかなり分離されている。

一方で、見知らぬ人への公開・有料販売には **未到達**。

| 聞き方 | 答え |
|---|---|
| 今のまま公開してよいか | **不可**（登録開放 × 運営負担の API × 規約なし × 個人情報の横断露出） |
| 家族・招待した知人だけなら | **条件付き可**（登録を閉じ、グループのユーザー一覧と public アルバムを直す） |
| SaaS として売るには | 下記のブロッカーを潰したあと、ストレージ課金モデル（仕様書 A/B）と Stripe が必要 |

最短の現実的パスは「いきなり不特定多数の SaaS」ではなく、**招待制のプライベート運用 → 安全な公開ベータ → 課金** の順。

## A. 今のままではだめなもの（公開ブロッカー）

公開した瞬間に、悪用・漏洩・法務・原価のいずれかが破綻する項目。  
**不特定多数にアカウントを渡す前に必須。**

### A1. 自己登録が無制限に開いている

- **現状:** `GET/POST /register`（`RegisterController`）。CAPTCHA・招待・承認待ちなし。メール＋表示名だけで Light アカウントが作れる。
- **なぜだめか:** Light でも Photos（20GB/人・運営 R2/B2）、翻訳（運営 DeepL）、音楽、YouTube 検索が使える。ボット1人で運営クラウドと API が破産する。
- **向き:** 当面は登録クローズまたは招待コード／管理者承認。公開するなら CAPTCHA ＋ 高コスト機能をデフォルト OFF。

### A2. 利用規約・プライバシー・同意がない

- **現状（対応済）:** `/terms` `/privacy`、登録時 `agreeTerms`。退会・エクスポート・Cookie・保持期間（おおよそ30日）・準拠法を記載。
- **残件:** 弁護士レビュー（販売前推奨）。
- **向き:** 完了（フェーズ1）。

### A3. グループ画面が全ユーザーのメールを出す

- **現状:** `GroupController::index` が `User::query()->...->toPublicArray()` を渡し、**全ユーザーの email / displayName / role** を Standard 以上に見せる。`toPublicArray()` には `pendingEmail` も含まれる。
- **なぜだめか:** 公開ディレクトリになる。スパム・なりすまし・個人情報漏洩。A4 の public アルバムと組み合わせると顔写真まで辿れる。
- **向き:** 一覧は自グループのみ。追加はメール完全一致検索か招待リンク。相手の承諾が必要。

### A4. アルバム「登録ユーザーに公開」がテナント横断

- **現状:** `AlbumVisibility::Public`。`PhotoService::canViewAlbum` は所有者以外でも `visibility=public` なら true。ログインしていれば見知らぬ人のアルバムが一覧に出る。
- **なぜだめか:** 家族向けの「みんなに見せる」が、公開 SaaS では「全顧客に見せる」になる。
- **向き:** テナント横断 public は廃止。グループのみ、または「リンクを知っている人」に変更。

### A5. グループメンバーを同意なく追加できる

- **現状:** `GroupService::addMember` はオーナーが任意 `user_id` を `firstOrCreate` するだけ。招待・承諾なし。
- **なぜだめか:** 他人のメモ・Todo（グループ共有はメンバーなら編集可）に巻き込める。
- **向き:** 招待リンク＋承諾。閲覧専用ロールがあると尚よい。

### A6. 運営 API キー1セットのまま、ユーザー課金がない

- **現状（一部対応）:** キーはアプリ全体1セットのまま。DeepL の DB キーは **暗号化**。高コスト機能は SA 限定＋ユーザー別日次上限。実徴収は未実装（フェーズ2）。
- **なぜだめか（残）:** 課金モデルが無いと一般公開のコスト転嫁ができない。
- **向き:** 招待制運用を維持しつつ、販売時に Stripe／顧客持ちキーを決める。

### A7. レート制限が無い

- **現状（対応済）:** ログイン／登録／パスワード／翻訳／アップロードに `throttle`。音声・鮮明化にも分あたり制限＋ユーザー別日次上限。
- **残件:** なし（値のチューニングは運用で）。
- **向き:** 完了。

### A8. 一般ユーザーが Google / LINE を自分で繋げない

- **現状（対応済）:** Google Calendar / LINE / Messenger の **個人連携** は **マイページ**（Standard / Light 可）。**チャネル設定（Bot トークン等）は Admin の設定**のまま。
- **残件:** なし（チャネルは運営共有のまま。顧客別 Bot はフェーズ2以降）。
- **向き:** 完了。

### A9. 退会とオブジェクト削除が無い

- **現状（対応済）:** マイページから本人退会（パスワード＋「退会」/ `DELETE` 確認）。`UserAccountDeletionService` で写真・音楽・メモ・Todo・グループ添付・連携を掃除してから User 削除（HTTP 応答後に実行）。管理者削除も同じ。マイページから JSON ZIP エクスポート可（メディア本体はメタデータのみ）。
- **残件:** 大規模アカウント向け本格キューワーカー、規約の弁護士レビュー。
- **向き:** 現状でフェーズ1として十分。販売前にバックアップ保持の運用を固定する。

### A10. 既知の管理者パスワード

- **現状:** Seeder / `tools/reset-admin-password.php` / README が `admin@example.com` / `admin12345`。
- **なぜだめか:** 本番で Seeder やツールを誤実行すると既知アカウントになる。
- **向き:** 本番で DatabaseSeeder を流さない。リセットツールは対話的な強力パスワードにするか削除。

### A11. Google Maps キーがフロントに出る

- **現状:** Map / Transit が JS API に `GOOGLE_MAPS_API_KEY` を埋め込む。
- **なぜだめか:** HTTP リファラ制限が無いと、盗用されて Maps 従量請求の標的になる。
- **向き:** Cloud コンソールでリファラ制限＋予算アラート。必要ならサーバ経由。公開前に必須。

## B. ネックになること（規模・原価・運用）

すぐ公開停止にはならないが、人数・データ量が増えると先に詰まるもの。

### B1. ストレージ原価（最大の変動費）

仕様書どおり、キーは運営共有。無料枠 **20GB × ユーザー数** が運営負担。

加えて実装ギャップ:

- **Music・メモ添付・グループ添付は写真クォータに含まれない**
- チャンクアップロードは完成時までクォータ未チェック（一時ファイルはローカル、最大およそ 3GB）
- 鮮明化（Stability）にユーザー別回数上限が無い
- 管理者／退会削除でオブジェクトが残ると課金だけ残る → **退会・管理者削除は `UserAccountDeletionService` で掃除（済）。** グループ共有・孤児エッジケースは要監視

販売モデル A（運営がクラウドを持ち従量請求）か B（顧客が自分のキー）かは `commercial-storage.md` の未決事項のまま。ここが決まらないと Stripe 設計に入れない。

### B2. AI / 翻訳 / 検索が運営持ちのまま使い放題

Light のデフォルトで使える高コスト機能:

| 機能 | ロール Light | 負担 |
|---|---|---|
| Photos アップロード | 可 | R2/B2 20GB |
| 翻訳 | 可 | DeepL 文字従量 |
| 音楽 | 可 | ストレージ（クォータ外） |
| 動画検索 | 可 | YouTube Data API |
| メモ／Todo 音声（LLM） | 可（キーがあれば） | OpenAI / Gemini |
| AI 鮮明化 | Photos 経由 | Stability クレジット |

使用量のユーザー別上限は DeepL キー全体の日次／月次のみ。LLM・YouTube・鮮明化はアプリ側にユーザー枠が無い。

### B3. 連携が「アプリに1本」

| 連携 | 現状 | 人数が増えると |
|---|---|---|
| Google OAuth クライアント | `.env` に1組 | 1プロジェクトで足りるが、`google_user_id` がグローバル unique のため同じ Google を家族で共有できない |
| LINE / Messenger | Webhook 1本、チャネル1つ | 全顧客が同じ Bot。顧客が自分の公式アカウントを持つ設計ではない |
| Maps | キー1つ | 呼び出し従量 |
| 休日・曜日ルール | `holiday_entries` / `weekday_rules` に `user_id` なし | Admin が休日を消すと全ユーザーのカレンダーが変わる |

### B4. Travel / 入出金が特定ライフスタイル固定

- Travel の初期プロファイルは 13A / RP / FUK↔MNL / Cebu Pacific（`TravelService::getOrCreateProfile`）。プロモ自動取得も Cebu Pacific 前提。cron が全ユーザー分をクロールする。
- 入出金は JP/PH タブ前提。

見知らぬユーザー向けの汎用 SaaS ではなく、**今の運営者家族の導線**。Standard に Travel を出すとノイズになる。製品として残すならオプトインか、Light 同様デフォルト非表示。

### B5. 単一サーバ／共有ホスト前提

- セッションは DB で複数台にも載せられるが、**写真のチャンクはローカルディスク**。複数インスタンスで壊れる。
- `QUEUE_CONNECTION=database`。`SyncPhotoToCloudinary` はキュー。本番の `queue:work` 手順は薄い。多くの処理は `afterResponse()`（リクエストプロセス依存）。
- cron: 写真コールドアーカイブ、毎分リマインダ、Travel プロモ取得。ユーザー増で線形に伸びる。ロリポップ想定の単一プロセス。
- アプリ内バックアップ・監視 UI・Sentry は無い。`GET /up` のみ。
- `.env.production.example` は `sa2-plus.com` 固定。Cloudinary フォルダ既定 `sa2todo`。

### B6. 認証が公開アカウント向けに弱い

- メール検証なし（`MustVerifyEmail` 未使用）
- 2FA なし
- ~~ログインは常時 remember（チェックボックスなし）~~（済・2026-08-21。チェックボックス化＋パスワード変更時に `remember_token` 破棄）
- ~~パスワード再設定に IP スロットルなし~~（済・2026-08-21。ログイン中の再送にも `throttle:auth-password`）

### B7. サービス層がコントローラ頼みの箇所

- `TodoService::listTodos(?int $userId = null)` は `$userId === null` だと **全件**。今のコントローラは userId を渡しているが、呼び出し漏れで全ユーザーの Todo が漏れる。
- グループ共有の Notes/Todos はメンバーならフル編集（閲覧専用なし）。

### B8. オンボーディングが「管理者の家族」前提

- 自己登録しても設定画面に入れない → Google / LINE を自分で繋げない。DeepL/LLM は管理者が入れたキーを消費する。
- ヘルプ・空状態の「最初の一歩」が製品として足りない。
- ロケールは ja/en のみ。ソース文字列は日本語。

## C. 公開して複数利用するために改善すること

実装チケットの順番案。UI 改善を優先する方針（`commercial-storage.md`）は維持し、**公開の安全側だけ先にやる**。

### フェーズ 0 … 招待した複数人で使う（最短）

ステータス: **実装済み（2026-08-12）**

「家族・知人」まで広げるなら、SaaS 化より先にここ。

1. 自己登録を閉じる、または招待コード必須にする → 管理画面「ユーザー管理」で設定（DB）。未設定時のみ `REGISTRATION_INVITE_CODE` がフォールバック（空なら閉鎖）
2. `/groups` の全ユーザー一覧をやめる（メール完全一致 or 招待）
3. アルバム public を「登録ユーザー全員」から外す（グループのみ。既存 public は本人のみ）
4. メンバー追加を承諾制にする（ダッシュボード／グループ画面で承諾・辞退）
5. ログイン・登録・翻訳・アップロードに `throttle`（テスト時は無効）
6. Maps キーに HTTP リファラ制限 → コードではなく Cloud コンソール。`.env*.example` に注記
7. 本番で Seeder / 固定パスワードツールを使わない（Seeder は production で例外。リセットツールは `FORCE_RESET_ADMIN=1` 必須）

これで「見知らぬ登録者」と「テナント横断の覗き見」は止まる。運営キー共有と 20GB は、人数が少なければ許容できる。
